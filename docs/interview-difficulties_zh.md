# 面试难点讲法：3 分钟主线 + 追问分支

> 配套阅读：[项目介绍.md](../项目介绍.md) §7（技术难点逐条展开）、§15（30 秒 / 2 分钟版本与简历描述）；[RTOS任务.md](../RTOS任务.md)（任务清单与并发原语）。
>
> 用法：背「3 分钟主线」，主线里预埋 3 个钩子，让对方顺着钩子追问；再按「追问分支」准备答法。

## 1. 3 分钟主线（口述稿）

> 我做的是一个 ESP32-S3 智能音箱固件。底座是开源语音助手：离线唤醒、云端 ASR/LLM/TTS、MCP 设备控制。我加的是——一条能独立启停的 WebRTC 点对点通话链路，支持浏览器和设备双向语音、设备摄像头单向视频上行，再往上是门铃界面和远程开门。
>
> 这个项目真正的难点不是把 WebRTC 跑起来，而是**语音助手和 WebRTC 要抢同一套硬件**：同一个 codec、同一条 I2S、同一个摄像头。
>
> 所以我做的第一件事是**资源移交**。我没有让 WebRTC 重新初始化音频，而是把助手已经建好的 `esp_codec_dev` handle 暴露给 WebRTC 媒体桥复用。通话开始时按固定顺序移交：暂停助手音频任务 → 挂起语音会话 → 释放摄像头 → 建媒体桥 → 起 PeerConnection；结束或者任何一步失败，都统一走一个**幂等的 Cleanup** 逆序恢复。幂等是必须的，因为本地挂断、对端离线、建连失败这三个事件可能重复触发同一个结束流程。
>
> 第二个是**通话期的回声消除**。通话切到 G711A 8 kHz 之后，助手原来的 AFE 不再处理这条链路，所以我给媒体桥单独建了一个 `esp_capture` 的 AEC 音源，用 ES7210 的 **MMR 布局**：两个近端麦克风，加一路真正的播放回采作为参考。这里我做了个取舍——如果板型声明自己有硬件参考能力、但实际创建不出 AEC 音源，我让它**直接启动失败**，而不是静默降级成裸麦克风。因为一个满是回声的通话，比一个明确失败的通话更糟。
>
> 第三块是**远程开门**。开门关系到一个物理动作，所以我没有相信信令通道：负责换 SDP/ICE 的信令通道，不应该天然拥有开门的权限。开门命令只接受**已经完成 WebRTC 握手的 DataChannel** 消息，信令通道的同名请求直接丢掉、也不回确认；再配上请求 ID、超时不自动重发、门锁忙的时候不重新计时、退出就恢复无效电平。
>
> 另外还有一层是**并发**：网络、音频、定时器、WebRTC 的回调都跑在不同 FreeRTOS 任务上。我的做法是事件组只负责置位，**所有状态修改回到主任务串行执行**；数据通路不用 `xQueue`，统一用 C++ 的 `deque` 加 `unique_ptr` 转移所有权，做到零拷贝。
>
> 最后我想说明边界：这个版本里，通话期间通过 WebSocket 的 MCP 控制可能不可达，本地信令还没有鉴权，AEC 效果我也没有量化数据——这些我都写在文档里，明确区分了源码完成、编译通过和实机跑通。

**主线里故意埋了 3 个钩子**：资源移交 / MMR 硬件参考 AEC / DataChannel 信任边界。钩子要能一句带过，让对方顺着问——你才有机会展开，而不是自己一口气讲完。

## 2. 追问分支

### 钩子 A：资源移交与幂等 Cleanup

**Q：Cleanup 为什么必须幂等？哪些事件会重复触发？**

结束有三个来源——本地挂断、对端离线、启动/建连失败，它们可能同时或先后到达，而且 WebRTC 回调本身在不同任务里。所以结束路径收敛成**单一出口**：任何失败分支都进同一个 `Cleanup()`，内部用标志位保证重复调用只是空转。顺序是移交的逆序：先拆 PeerConnection 和媒体桥，再恢复摄像头，最后把 24 kHz 的助手音频和会话能力恢复回去。

**Q：怎么保证「上一批使用者真的退出了」才移交？**

这是我改动过的一处隐式时序假设。原来 `Suspend()` 是 `vTaskDelay(50ms)` 硬等——这是赌任务 50 ms 内一定退出，一旦它卡在读 codec 上，WebRTC 就会打开还在被占用的设备。我改成**任务退出确认**：停止后确认输入/输出任务已经退出，带 500 ms 有界超时兜底。**目前的实现是 `eTaskGetState` 轮询**，更好的做法是任务退出时置事件组位、主任务阻塞等待——这样能和全项目「事件组通知」的模式统一，也消除忙等，这一条我写在待办里。

### 钩子 B：MMR 硬件参考 AEC

**Q：MMR 的两个 M 一个 R 是什么？**

M = 麦克风近端通道（ES7210 上两路），R = 播放回采参考。立创板 ES7210 走 4 时隙 TDM，AFE 只取前三路，所以布局是 M-M-R、有效时隙掩码 `0x07`。

**Q：硬件参考为什么比「软件复制待播放 PCM」好？**

软件参考只是把「我准备播什么」复制一份，但真实回声经过了解码、增益、DAC、功放和扬声器，幅度和相位都变了；硬件回采拿到的是**实际播放出来的信号**，更接近真实回声路径。

**Q：为什么宁可直接失败也不降级？**

降级后的链路是强回声的裸麦克风，对方体验非常差，而且问题会被掩盖——没人知道 AEC 没生效。**声明了能力就必须兑现**，创建不出来是配置或硬件问题，应该暴露出来。

### 钩子 C：DataChannel 信任边界

**Q：为什么只信 DataChannel？**

信令通道的职责是交换 SDP 和 ICE，它天然是「不可信」的，而且本地信令端点当前没有鉴权、公网房间号也可能被猜中。DataChannel 至少能保证**命令来自完成 DTLS/SCTP 握手的对端**，所以我把「消息来自哪条通道」一路传到业务层作为授权判断。

**Q：DataChannel 解决了什么，没解决什么？** ← 这题最容易翻车，一定要主动说

它解决的是**消息的完整性来源**，不解决**谁有资格成为对端**。如果攻击者猜中房间号先连上了，他照样是合法的 DataChannel 对端。所以本地信令只适合受控局域网演示，要产品化必须补设备端一次性配对码 + HttpOnly 会话 Cookie + 同源校验和重放防护。**不要把它讲成「安全的门禁方案」。**

### 钩子 D：并发模型（备用钩子）

**Q：为什么音频数据通路不用 `xQueue`？**

数据通路传的是带指针的音频包，用 FreeRTOS 队列要么拷贝、要么自己管内存；用 `std::deque` + `std::unique_ptr` 直接把所有权转移过去，零拷贝，而且接口更顺手。

**Q：那 FreeRTOS 原语和 C++ 原语怎么分工？**

FreeRTOS 原语只负责**事件通知**（事件组、任务通知），C++ 原语负责**数据传递与互斥**（`deque` / `mutex` / `condition_variable` / `atomic`）。全项目没有一个 `xSemaphoreCreateMutex`，职责不重叠。配套有一条硬约束：`esp_timer` 回调里绝对不能 `vTaskDelay`——所有回调在同一个高优先级任务上串行，阻塞会拖住整机。

### 钩子 E：被问「没做完的部分」

**Q：通话期间模型能控制设备吗？**

**现阶段不能宣称可以，而且是设计层面的问题**：WebSocket 路径把控制 JSON、MCP 和二进制音频放在同一个连接里，关闭音频通道会把整个 WebSocket 释放掉，于是 `start` 之后的 `stop` / `get_stats` 可能失去通道。正确解法是把**控制面与音频数据面解耦**，但那需要和服务端一起定义独立会话标识，不是设备端单方面能改的。

**Q：AEC 效果怎么样？** ← 千万别说「很好」

**我没有量化数据。** 我能说的是接入了硬件参考 AEC 通道；要证明效果得测双讲、收敛时间和长时间时钟漂移，用录音样本加示波器看参考电平——这在我的待办里。**不要编 RTT、丢包率、回声抑制量这类数字。**

## 3. 三条通用原则

1. **先讲冲突，再讲方案**：每个难点都用「两个需求打架 → 我的取舍 → 代价是什么」来讲，比罗列功能有说服力得多。
2. **主动暴露边界**：未完成的、没实测的，自己先说。文档里已经严格区分「源码完成 / 编译通过 / 实机跑通 / 量化验证」，把这个口径保持住，可信度会高一个档。
3. **不要吹「安全」**：凡是提到门禁/开锁，都主动加一句「DataChannel 只保证来源，不保证身份」。
